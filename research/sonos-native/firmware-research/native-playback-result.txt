Native UDP playback demonstrated — 14 October 2026

Firmware-informed change
The older ChangeTransportSettings handler rejects nonzero state at object
field 0x54f4. Nearby code associates this state with transport/group roles.
We tested the group-member interpretation on the live firmware: with the two
speakers initially standalone, muted Server Room was temporarily joined to
Airplay Connect using x-rincon:<Connect UUID>. The same ChangeTransportSettings
request previously rejected with 800 then succeeded.

Confirmed live evidence
- Muted 10-second test: 1756 generated audio packets sent, 20 clock requests
  received and answered, receiver reported PLAYING/OK.
- Audible 8-second test: synthesized 440 Hz tone, volume 15; 1405 packets and
  16 clock exchanges. User explicitly confirmed hearing the tone.
- User requested repetition at volume 25. The 20-second repeat sent 3513 packets
  and answered 40 clock requests; receiver reported PLAYING/OK.
- No reported restoration errors in these runs. Receiver source, group role,
  volume and mute were restored by the test code.

Scope of achievement
This establishes native UDP audio playback from our own sender on this Play:3,
with application-layer clock replies, using ordinary HTTP control calls.
No TLS device certificate was needed for this particular group-member route.
Audio was generated by the Mac, not relayed from the Connect's physical input.
The real Connect is still used to establish legitimate group membership and
provide initial transport settings. A wholly independent virtual Sonos source
has NOT been demonstrated. Do not claim that every authentication issue is solved.
No end-to-end AirPlay latency or long-running stability measurement yet.

Implementation
probe.py --group-member uses the working route. --tone generates 440 Hz;
--tone-volume allows 0..25. --wav accepts stereo 16-bit 44100 Hz PCM WAV.
Runs remain bounded to 1..20 seconds and require both devices initially
standalone and the receiver initially on the specified line-in source.
The test changes only the target receiver's volume/mute and temporary group
membership. Restore paths return it to its initial source and playback state.

Next work
Validate WAV music, sustained clock/packet behaviour, then integrate an opt-in
native sender with AirConnect's decoded PCM. Investigate removing the real
Connect dependency separately. Keep the production HTTP bridge as fallback.

Further validation
The user confirmed clear recovered music from the Python sender (15 s).
The C engine then sent 3513 packets over a 20-second music test, answered
40 clock requests and reported zero packets more than 6 ms late. The user
confirmed this C-engine music run sounded good. C codec matched all 13,826
captured audio packets exactly. C packet/sender tests passed with ASan/UBSan
on macOS and compiled/passed natively with GCC 4.9 on the ARMv7 CloudKey.
The bridge application itself remains unchanged; integration is still pending.
