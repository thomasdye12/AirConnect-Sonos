Conclusion
The emulated-device route encounters an observed certificate trust check on
current firmware 86.10-80260. A listener and self-signed certificate do not
satisfy it. This is stronger evidence than the earlier TLS handshake alone.
It does not prove all possible Connect-free control routes are impossible.
No genuine Sonos private keys were downloaded, copied or used. No firmware
was flashed, no trust setting changed, and no production service replaced.
All bounded playback probes reported no restoration errors. Discovery
advertisements were withdrawn and experimental network listeners closed.

Remaining research
- Trace an independently usable virtual-input session API on current firmware,
  including session creation, endpoint direction and audio framing. The old
  binary contains x-sonos-vli and /websocket/vli, but strings are not a working API.
- Determine whether there is a supported enrollment path for a software source
  or another control path that leaves the genuine receiver as coordinator.
- Do not claim success based on topology presence, HTTP 200, or packet sends:
  require clock exchanges, clean audible output, and no Connect setup calls.
- After independent setup works, validate separate simultaneous AirPlay streams
  to different rooms. The user explicitly wants independent sessions, not
  one shared multiroom stream.
